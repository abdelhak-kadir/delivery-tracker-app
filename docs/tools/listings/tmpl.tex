\chapter{Implementation}\label{chap:implementation}
\label{ch:implementation}

This chapter describes how the architecture and the pipeline designed in Chapter~\ref{chap:design} were realized in code. It follows the order in which the system was built: the development environment and the repository layout (Section~\ref{sec:impl-env}), the Spring Boot backend (Section~\ref{sec:impl-back}), the React frontend (Section~\ref{sec:impl-front}), the container images (Section~\ref{sec:impl-docker}), the Terraform infrastructure (Section~\ref{sec:impl-terraform}), the Ansible configuration (Section~\ref{sec:impl-ansible}) and, finally, the GitHub Actions workflows that tie these parts together (Section~\ref{sec:impl-cicd}). Measurements and scan results are presented in Chapter~\ref{chap:results}.

All listings are verbatim excerpts of the files named in their captions. To keep them short, import statements and trailing line comments are omitted, and elided passages are marked with a comment containing three dots.

\section{Development Environment and Repository Layout}
\label{sec:impl-env}

\subsection{Technology Baseline}

The backend is a Java~21 application built with Maven (through the Maven wrapper \texttt{mvnw}) on Spring Boot~3.5.16 (3.5.6 at the time of the measurements of Chapter~\ref{chap:results}). The main dependencies are Spring Web, Spring Data JPA with the PostgreSQL driver, Spring Security, Bean Validation, the \texttt{jjwt}~0.12.5 library for JSON Web Tokens, Lombok, and \texttt{springdoc-openapi-starter-webmvc-ui}~2.8.9 for the OpenAPI description and Swagger~UI. The Actuator starter exposes the health endpoint. H2 and \texttt{spring-security-test} are declared for the test scope, and the JaCoCo Maven plugin (0.8.12) is configured to produce coverage reports. The frontend is a Create React App project using React~19.1, Material~UI~7.3, React Router~7 and Axios. The database is PostgreSQL~16.

\subsection{Repository Layout}

The whole system lives in a single repository, organized by concern (Listing~\ref{lst:app-tree} in the appendices). The directory \texttt{docs/} holds this report.


\subsection{Configuration and Local Execution}

Runtime configuration is injected through environment variables, never committed. The file \texttt{.env.example} documents the seven variables the application needs: the database name, user and password (\texttt{POSTGRES\_DB}, \texttt{POSTGRES\_USER}, \texttt{POSTGRES\_PASSWORD}), the signing secret of the tokens (\texttt{JWT\_SECRET}), the credentials of the application user (\texttt{APP\_USER\_USERNAME}, \texttt{APP\_USER\_PASSWORD}) and the list of origins allowed by CORS (\texttt{APP\_CORS\_ALLOWED\_ORIGINS}, which defaults to the two local development origins). Developers copy it to a local \texttt{.env} file, which is ignored by Git.

Spring configuration is split into a common file and two profiles. \texttt{application.yaml} holds only the application name and the Actuator exposure (the health endpoint alone is exposed). The \texttt{local} profile points the datasource at \texttt{localhost:5432} and lets Hibernate update the schema; the \texttt{docker} profile defines the application user and token settings from the environment, the datasource being supplied by Compose variables. In both, the token lifetime is set to 1\,800\,000~ms, i.e.\ 30 minutes. No further profiles exist: the staging and production environments differ in their infrastructure and Ansible variables, not in Spring profiles.

Two ways of running the system locally are provided. The script \texttt{back/start-local.sh} loads \texttt{.env} and runs \texttt{./mvnw spring-boot:run} with the \texttt{local} profile, which is convenient when a PostgreSQL instance is already available. The script \texttt{start.sh} at the repository root stops any running stack and rebuilds and starts the three containers defined in \texttt{docker/docker-compose.local.yaml} (Section~\ref{sec:impl-docker}).

\section{Backend: Spring Boot REST API}
\label{sec:impl-back}

\subsection{Package Structure}

The backend follows a classical layered architecture. Requests enter through the controllers of the \texttt{controller.v1} package, which delegate to service interfaces implemented in \texttt{service.serviceimpl}; the services use Spring Data repositories (\texttt{repository}) and translate between entities (\texttt{entity}) and transfer objects (\texttt{dto.v1}) with hand-written components in \texttt{mapper}. Cross-cutting code lives in \texttt{config} (security, CORS, OpenAPI, API path constants) and \texttt{exception} (error model and global handler). The constants of \texttt{ApiPaths} compose the versioned prefix \texttt{/api/v1}.

\subsection{Entities and Persistence}

Three JPA entities map the domain: \texttt{Client} (name and identity number), \texttt{Driver} (name and plate number) and \texttt{TransportLog}, the central business record of the haulage company. A transport log references one client and one driver through \texttt{@ManyToOne} associations and stores the load and unload dates and locations, the destination, the delivery note, and the monetary and fuel figures of the trip (advance, fuel quantity and price per liter, variable charge, charge price, client tariff and trip price), together with the operator and the commercial responsible for it. Monetary amounts use \texttt{BigDecimal}, identifiers are generated by the database, and Lombok generates accessors and builders. The three repositories simply extend \texttt{JpaRepository}; all queries are therefore derived by Spring Data and parameterized, so no SQL string is concatenated anywhere in the code. The schema itself is created and updated by Hibernate (\texttt{ddl-auto: update}); no migration tool such as Flyway is used.


\subsection{Data Transfer Objects and Mappers}

The API never exposes entities. Every module has a creation request, an update request and a response, all declared as Java records, which are immutable and concise. Validation rules are attached to the record components with Jakarta Bean Validation; for transport logs, for instance, the client and driver identifiers, the dates and all monetary fields are mandatory. Two generic records complete the model: \texttt{BaseResponse<T>} wraps every successful answer with a success flag, a message and the payload, and \texttt{PagedResponse<T>} carries a page of results with its metadata.


The conversion between records and entities is done by one \texttt{@Component} per module. Explicit mappers were preferred to a generation library such as MapStruct: with three small entities they are easy to read and to debug. The mapper of transport logs additionally receives the already loaded client and driver, and delegates the nested conversions to the two other mappers.


\subsection{Services}

Each service is an interface with an implementation in \texttt{serviceimpl} receiving its collaborators by constructor injection. The implementations contain the use-case logic: loading by identifier and raising a \texttt{ResourceNotFoundException} when the entity does not exist, updating (the client service loads the entity, applies the new name and identity number and saves it), deleting (a delete request for an identifier that does not exist is also reported as not found rather than as an internal error), and building the paginated answer from a Spring Data \texttt{Page}. The transport-log service is the only one that spans several aggregates: its create and update operations are \texttt{@Transactional} and first resolve the referenced client and driver, so that a request naming an unknown one fails with a not-found error before anything is written.


\subsection{Controllers and OpenAPI Documentation}

The controllers expose the same five operations on each resource, summarized in Table~\ref{tab:endpoints}. Updates carry the identifier in the request body, which is why \texttt{PUT} has no path parameter. The collection endpoints accept the zero-based \texttt{page} parameter (default 0) and the \texttt{size} parameter (default 10, constrained to the range 1--100 by Bean Validation on a \texttt{@Validated} controller). The path of the transport-log resource is \texttt{/trans\_logs}.

Errors are returned in a uniform JSON body (Section~\ref{sec:impl-errors}): \texttt{400} for an invalid payload, \texttt{401} for a missing, malformed or expired token or wrong credentials, \texttt{403} when access is denied, \texttt{404} when the identifier (or the referenced client or driver) does not exist, and \texttt{500} for any other failure.

Every controller is annotated for springdoc: \texttt{@Tag} groups the operations, \texttt{@Operation} describes each of them, and \texttt{@ApiResponse} declares the success and error bodies by pointing to \texttt{BaseResponse}, \texttt{PagedResponse} and \texttt{ErrorResponse}. A class-level \texttt{@SecurityRequirement} annotation (scheme \texttt{BearerAuth}) marks the endpoints as requiring the bearer scheme declared once in \texttt{OpenApiConfig}, where the title, version, license and server of the API are also defined. The login operation overrides the requirement with an empty one so that Swagger~UI does not demand a token for it. The specification is served at runtime as \texttt{/v3/api-docs} (JSON) and \texttt{/v3/api-docs.yaml}, and the workflow \texttt{openapi-docs.yml} (Section~\ref{sec:impl-cicd}) publishes a static Swagger~UI built from it to GitHub Pages after each successful backend pipeline on the main branch.


\subsection{Security}
\label{sec:impl-security}

Security is implemented with Spring Security in a stateless configuration. Figure~\ref{fig:jwt-flow} summarizes the flow, and the components are described below.

\input{figures/fig6-2}

\paragraph{Authentication model.} The application has a single account, whose name and password are supplied through the environment variables \texttt{APP\_USER\_USERNAME} and \texttt{APP\_USER\_PASSWORD} and bound to the properties \texttt{app.user.*}; its role is \texttt{ROLE\_ADMIN}. The \texttt{SimpleUserDetailsService} hashes the configured password with BCrypt once, in a \texttt{@PostConstruct} method, discards the clear-text value, and returns a \texttt{UserDetails} object only for the configured user name. There is no user table, no registration and no role differentiation: \texttt{@EnableMethodSecurity} is switched on, but no method-level rule is currently declared, and every authenticated request is treated alike.


\paragraph{Token issuance.} The \texttt{AuthController} passes the credentials of a validated \texttt{LoginRequestDto} to the \texttt{AuthenticationManager}. On success, the \texttt{JwtTokenProvider} builds a signed token whose subject is the user name and whose \texttt{roles} claim lists the authorities; it is signed with an HMAC key derived from \texttt{JWT\_SECRET} and expires after the configured 30 minutes. The response contains the token, the user name and the expiry time. No refresh token exists: when the token expires, the user logs in again.


\paragraph{Request filtering.} The \texttt{JwtAuthenticationFilter}, a \texttt{OncePerRequestFilter} registered before the standard username/password filter, skips the public paths, extracts the token from the \texttt{Authorization: Bearer} header, validates its signature and expiry, loads the user and stores an authentication object in the security context. An invalid or missing token leaves the context empty, and the decision is then taken by the authorization rules of the filter chain: only the login route, the Actuator health endpoint, Swagger~UI and the OpenAPI document are public, and \texttt{anyRequest().authenticated()} applies to everything else, including all \texttt{/api/v1/clients} endpoints; the filter itself contains no exception for any business path. The chain also registers an \texttt{authenticationEntryPoint} and an \texttt{accessDeniedHandler} that write the same JSON \texttt{ErrorResponse} as the rest of the API (status, error label, message, request path, timestamp) with the status \texttt{401} for an unauthenticated, invalid or expired token and \texttt{403} for a denied access. Without them, Spring Security would answer an unauthenticated request with an empty \texttt{403}, which the frontend could not distinguish from a permission problem. Sessions are disabled and CSRF protection is switched off, which is appropriate for an API that authenticates every request with a bearer token and keeps no cookie-based session.



\paragraph{Cross-origin requests.} \texttt{CorsConfig} registers a \texttt{CorsConfigurationSource} that allows the origins listed in the property \texttt{app.cors.allowed-origins}, which is filled from the environment variable \texttt{APP\_CORS\_ALLOWED\_ORIGINS} and defaults to the development origins \texttt{http://localhost:3000} and \texttt{http://127.0.0.1:3000}; it also allows the usual HTTP methods, any header and credentials, and exposes the \texttt{Authorization} header. The Ansible environment template sets the same variable on the servers. In the deployed topology the browser talks to the same origin as the frontend, because nginx proxies \texttt{/api} to the backend (Section~\ref{sec:impl-front}).

\subsection{Error Handling}\label{sec:impl-errors}

A \texttt{@ControllerAdvice} class, \texttt{GlobalExceptionHandler}, converts exceptions into one JSON body, the record \texttt{ErrorResponse} (status, error label, message, request path, timestamp). Failed Bean Validation yields a 400 response listing the offending fields, \texttt{ResourceNotFoundException} a 404, \texttt{BadCredentialsException} a 401 with a deliberately generic message, and any other exception a 500. Failures detected before a request reaches a controller (a missing, malformed or expired token, or a denied access) are reported by the security configuration with the same body and the status 401 or 403, as described above. The \texttt{@ApiResponse} annotations reference the same body type, so the documented and the actual error formats coincide.

\subsection{Test Strategy}

The backend tests follow the layers of the application. The Driver module served as the reference implementation of each level, which was then reproduced for the Client and TransportLog modules; the authentication controller and the security behavior are covered as well. The suite contains 82 tests, all passing in the last run, which measured a JaCoCo line coverage of 77.1\,\% (see Chapter~\ref{chap:results}).
\begin{itemize}
  \item \textbf{Unit tests of the service layer} use JUnit~5 and Mockito: the repository and the mapper are mocks, and the tests verify the returned value and the interactions.
  \item \textbf{Web-layer tests} use \texttt{@WebMvcTest} with \texttt{MockMvc}. The service is replaced by a \texttt{@MockBean}, and the test imports a \texttt{TestSecurityConfig} that registers the real JWT components but a permissive filter chain, so that the tests concentrate on routing, validation and serialization. Both success cases (201, 200) and failure cases (400 for invalid input, 404 for an unknown identifier) are covered; the same slice is used for the \texttt{AuthController}, including the 401 answer to bad credentials.
  \item \textbf{Repository tests} use \texttt{@DataJpaTest}, which starts only the JPA slice against an in-memory H2 database and provides a \texttt{TestEntityManager} for fixtures.
  \item \textbf{Integration tests} use \texttt{@SpringBootTest} with \texttt{@AutoConfigureMockMvc}: the whole context is loaded, the properties normally supplied by the environment (token secret, application user) are provided with \texttt{@TestPropertySource}, an authenticated user is simulated with \texttt{@WithMockUser}, and the table is emptied before each test.
  \item \textbf{Security integration tests} (\texttt{SecurityIntegrationTest}) load the real filter chain, not the permissive test configuration. They check that a request without a token, with a malformed token and with an expired token to a business endpoint (including the client endpoints) is answered with \texttt{401}, that a wrong password yields \texttt{401}, and that a valid login followed by a request carrying the issued token gives access.
\end{itemize}
The JaCoCo plugin instruments the test run, and the continuous-integration pipeline uploads its report to Codecov (Section~\ref{sec:impl-cicd}).

\section{Frontend: React Single-Page Application}
\label{sec:impl-front}

\subsection{Structure}

The source tree of \texttt{front/src} separates presentation from infrastructure code. The \texttt{components} folder contains one sub-folder per screen (\texttt{Auth}, \texttt{Dashboard}, \texttt{Clients}, \texttt{Drivers}, \texttt{TransportLogs}), a \texttt{Layout} component providing the application bar, the navigation menu and the logout action, and a \texttt{Common} folder with the reusable pieces: \texttt{DataTable}, \texttt{ConfirmDialog}, \texttt{LoadingSpinner} and \texttt{ErrorBoundary}. The folder \texttt{contexts} holds the \texttt{AuthContext}, \texttt{services} the Axios client in \texttt{api.js}, and \texttt{utils} some formatting helpers.

\subsection{Routing and Route Protection}

Navigation uses React Router. The public \texttt{/login} route is wrapped in a \texttt{PublicRoute}, which redirects an already authenticated user to the dashboard; all other screens are children of a single route rendering the \texttt{Layout} and wrapped in a \texttt{ProtectedRoute}, which shows a spinner while the stored session is being restored and redirects anonymous visitors to the login page. Unknown paths fall back to the dashboard. Because there is only one role, navigation is the same for every user. This protection is a usability feature; the authoritative checks are performed by the backend on every request.


\subsection{Authentication State and HTTP Client}

The \texttt{AuthContext} exposes the authentication state (\texttt{isAuthenticated}, \texttt{user}, \texttt{loading}) and the \texttt{login} and \texttt{logout} functions through a provider and a \texttt{useAuth} hook. The login function calls the backend, validates the shape of the answer, and only then marks the session as authenticated; there is no local or simulated login path. On success, the token and the user name are written to \texttt{localStorage}, and at application start the provider restores the session from the same keys. Keeping the token in \texttt{localStorage} survives page reloads but makes it readable by any script running in the page; this trade-off is discussed with the limitations.

All backend calls go through one Axios instance. A request interceptor reads the token from \texttt{localStorage} and adds the \texttt{Authorization: Bearer} header. A response interceptor translates failures into user-facing messages stored in \texttt{error.userMessage} (time-out, network error, 403, 5xx, or the \texttt{message} returned by the API) and, on a 401 response, removes the stored session and redirects to the login page. The module finally exports one small object per resource (\texttt{clientsAPI}, \texttt{driversAPI}, \texttt{transportLogsAPI}) whose methods mirror the endpoints of Table~\ref{tab:endpoints}. The base URL of the instance is \texttt{process.env.REACT\_APP\_API\_URL} when that variable is set at build time and the relative path \texttt{/api/v1} otherwise. A relative URL works in both execution modes: in the containers, nginx proxies \texttt{/api/} to the backend, and in local development the \texttt{proxy} entry of \texttt{package.json} makes the Create React App development server forward unknown requests to \texttt{http://localhost:8080}. The same build can therefore be deployed to any host without recompilation.


\subsection{Screens and Reusable Components}

The \textbf{Dashboard} issues three requests in parallel with \texttt{Promise.all}: it reads the \texttt{totalElements} field of a one-element page of clients and of drivers to display the counts, and fetches the first five transport logs. The \textbf{Clients} and \textbf{Drivers} screens share the same pattern: a paginated \texttt{DataTable}, a dialog containing the creation and edition form with field-level validation, a \texttt{ConfirmDialog} before deletion, and a \texttt{Snackbar} reporting success or failure. The \textbf{Transport logs} screen uses a larger form: the client and the driver are chosen through \texttt{Autocomplete} fields fed by the corresponding endpoints, and mandatory and numeric fields are checked before submission. The monetary values, including the trip price, are entered by the operator; the application records them but does not derive one from another.

\texttt{DataTable} is a generic component driven by a column description and by the pagination state (\texttt{page}, \texttt{size}, \texttt{totalElements}) held by the parent, which maps directly onto the server-side pagination of the API. \texttt{ErrorBoundary} catches rendering errors below it and displays a recovery screen instead of a blank page. The data-loading functions of the three management screens are wrapped in \texttt{useCallback} so that they can be listed as dependencies of the \texttt{useEffect} hooks that call them. The frontend test suite is limited to smoke tests in \texttt{App.test.js}, which the pipeline nevertheless executes.

\subsection{Serving the Application with nginx}

In the container image the compiled application is served by nginx. The \texttt{location /} block implements the single-page-application fallback with \texttt{try\_files}, so that deep links such as \texttt{/drivers} are answered by \texttt{index.html}; static assets are cached for a year, whereas HTML is never cached. The \texttt{location /api/} block proxies requests to the container named \texttt{spring-boot-app} on port 8080, forwarding the client address and protocol headers and setting 30-second time-outs; Swagger~UI and the OpenAPI document are proxied likewise. The server also enables gzip compression, adds the headers \texttt{X-Frame-Options}, \texttt{X-Content-Type-Options}, \texttt{X-XSS-Protection}, \texttt{Referrer-Policy} and a \texttt{Content-Security-Policy}, denies access to hidden files, and answers \texttt{/health} directly, which the image health check relies on.

\section{Containerization}
\label{sec:impl-docker}

\subsection{Backend Image}

The backend image is built in two stages. The first stage uses the Temurin JDK~21 image, copies \texttt{pom.xml} and the Maven wrapper before the sources and resolves the dependencies in a separate layer, so that Docker's layer cache is reused as long as the dependencies do not change; the application is then packaged with the tests skipped, since they have already been executed by the pipeline before the image is built. The second stage starts from the Temurin JRE~21 image, which contains no compiler or build tool, creates a dedicated system user and group, copies only the executable JAR owned by that user, and runs the application as this unprivileged user. A compromised process thus does not hold root privileges inside the container.


\subsection{Frontend Image}

The frontend image also has two stages: Node~20 on Alpine compiles the React application with \texttt{npm ci} and \texttt{npm run build}, and the resulting static files are copied into an \texttt{nginx:alpine} image together with the nginx configuration described above. The runtime stage upgrades the Alpine packages, installs \texttt{curl} for the health check, gives the \texttt{nginx} user ownership of the cache, log and content directories, and switches to \texttt{USER nginx}. A \texttt{HEALTHCHECK} instruction polls the \texttt{/health} location every 30 seconds so that Docker reports the container as unhealthy if nginx stops answering. The file is named \texttt{dockerfile} in lower case in the repository.


\subsection{Compose Files}

Three Compose files live in \texttt{docker/}. \texttt{docker-compose.local.yaml} builds the backend and the frontend from the sources and starts a \texttt{postgres:16-alpine} database; it is the file used by \texttt{start.sh}. The other two use an already built backend image (\texttt{docker-compose.back.yaml} starts only the backend and the database). In all of them the services share a bridge network, and the database keeps its data in the named volume \texttt{db\_data}, so that the data survive container re-creation (Figure~\ref{fig:docker-arch}).

\input{figures/fig6-1}

The startup order is guarded by a health check rather than by a mere \texttt{depends\_on}: the database service declares a \texttt{pg\_isready} probe, and the backend waits for the condition \texttt{service\_healthy} before starting. This avoids the Spring application opening its connection pool before PostgreSQL accepts connections. All credentials are taken from the \texttt{.env} file through variable substitution, and the profile \texttt{docker} is activated through \texttt{SPRING\_PROFILES\_ACTIVE}.

\section{Infrastructure as Code with Terraform}
\label{sec:impl-terraform}

\subsection{Root Configuration}

The \texttt{infra/} directory is a Terraform root module for the DigitalOcean provider (version constraint \texttt{\textasciitilde{}> 2.43}, Terraform 1.5 or later). The state is kept in a remote backend hosted by Terraform Cloud, which provides state locking and avoids storing state files in the repository; the provider token is a sensitive variable supplied by the pipeline.

\texttt{main.tf} creates one VPC shared by the two environments and instantiates the module \texttt{modules/stack} twice, once as \texttt{staging} and once as \texttt{production}. The environments differ only in the arguments passed to the module, mainly the droplet sizes, which are defined as variables with different defaults (a larger frontend and backend for production). Figure~\ref{fig:vpc-architecture} shows the resulting topology.


\input{figures/fig5-1}

Variable validation is used to encode a security rule directly in the interface of the configuration: the list of CIDR blocks allowed to reach the bastion over SSH is rejected if it contains \texttt{0.0.0.0/0}.


\subsection{The \texttt{stack} Module}

The module encapsulates everything an environment needs and is parameterized by the environment name, the region, the VPC identifier, the SSH keys, the application port and the sizes of the machines. It creates:
\begin{itemize}
  \item three droplets (bastion, frontend, backend) from an Ubuntu~22.04 image, attached to the VPC, with DigitalOcean monitoring enabled and tagged by environment and role. Their cloud-init script only refreshes and upgrades the package cache; all software installation is left to Ansible;
  \item three cloud firewalls bound to these droplets: the bastion accepts SSH only from the administrator CIDR blocks; the frontend accepts ports 80 and 443 from anywhere and SSH only from droplets tagged as bastion; the backend accepts SSH only from the bastion and the application port only from droplets tagged as frontend. Tag-based sources keep the rules valid when addresses change;
  \item a managed PostgreSQL cluster (engine and version from variables, a single node of the smallest size, attached to the private network, with a Monday maintenance window), a database named after the environment, and a database firewall whose only rule admits the backend droplet.
\end{itemize}


\subsection{DNS and Outputs}

\texttt{dns.tf} declares the DNS domain managed by DigitalOcean with public records for the frontend and the bastion of each environment and private records for the frontend and backend droplets, which resolve to addresses inside the VPC. \texttt{outputs.tf} exports the resulting names and the database host of each environment. These outputs are the interface with Ansible: the inventory generator reads them in JSON form (Section~\ref{sec:impl-ansible}), so that no address is copied by hand.

\subsection{Policy as Code with OPA}

Custom guardrails complement the generic scanners. Two Rego files in \texttt{infra/policy/}, written in the \texttt{rego.v1} dialect and sharing the package \texttt{terraform.security}, define \texttt{deny} rules evaluated against the JSON rendering of the Terraform plan. Seven checks are implemented in total (Table~\ref{tab:rego}).
\begin{itemize}
  \item \texttt{bastion\_access.rego} forbids SSH rules open to \texttt{0.0.0.0/0} or \texttt{::/0} on every firewall other than the bastion's, forbids the same on the bastion's firewall, and requires a source address on the bastion's SSH rule.
  \item \texttt{droplet\_config.rego} restricts droplet images to an approved list, requires at least one SSH key on every droplet when the key list is known at plan time, requires the tag \texttt{role:bastion-<env>} on the bastion droplet, and requires an \texttt{env:} tag on every droplet.
\end{itemize}
Two lessons of the first version shaped the current rules. Resources of the stack module appear in the plan with addresses of the form \texttt{module.staging.digitalocean\_firewall.frontend\_fw}, so the rules select resources by their type and planned name rather than by a Terraform address or an expression such as a droplet identifier, which is only known after the apply. The firewalls, in turn, select the bastion by the tag \texttt{role:bastion-<env>}, which is why the absence of that tag is itself a violation. The earlier rule requiring \texttt{fail2ban} in the user data was removed, because fail2ban is installed by Ansible and not by cloud-init.


The rules were checked locally with Conftest against two synthetic plans written for the purpose: a compliant plan passed all seven checks, and a non-compliant plan produced seven failures, one per check. No real Terraform plan was evaluated during this verification, so the behavior on the full output of the provider is not demonstrated. The rules are executed by Conftest in the Terraform workflow, with the option \texttt{--namespace terraform.security} so that the package is selected explicitly, and by OPA in a pull-request check (Section~\ref{sec:impl-cicd}).

\section{Configuration Management with Ansible}
\label{sec:impl-ansible}

\subsection{Layout}

The \texttt{ansible/} directory is organized as follows.
\begin{itemize}
  \item \texttt{playbooks/}: \texttt{bootstrap.yml}, \texttt{deploy.yml} and \texttt{migrate-to-ansible-user.yml}.
  \item \texttt{roles/}: twelve roles, described in Table~\ref{tab:roles-impl}.
  \item \texttt{group\_vars/}: variables common to all hosts and to the bastions, and one folder per environment holding a plain \texttt{main.yml} and an encrypted \texttt{vault.yml}.
  \item \texttt{inventories/}: the generated inventory; \texttt{scripts/}: the inventory generator and an SSH test script; a \texttt{Makefile} gives each operation a short, uniform command.
\end{itemize}
\texttt{ansible.cfg} sets the defaults: the remote user is the service account \texttt{ansible}, host-key checking is enabled, facts are cached, and the SSH arguments enable agent forwarding and connection multiplexing. Pipelining and SFTP are disabled to avoid problems with the proxied SSH connections.

\subsection{Inventory Generated from Terraform}

The inventory is never written by hand. The Makefile target \texttt{inventory} exports the Terraform outputs to JSON and runs \texttt{scripts/generate\_inventory.py}, which builds the groups \texttt{staging}, \texttt{production}, \texttt{bastion}, \texttt{frontend}, \texttt{backend} and \texttt{app\_servers} from the DNS names found in the outputs and stores the database host of each environment as a variable. The generated file is not versioned. The bastion is contacted directly, whereas the frontend and backend hosts, reachable only through the private network, receive an \texttt{ansible\_ssh\_common\_args} value with \texttt{-o ProxyJump} through the bastion and agent forwarding. The target ends with a connectivity test of all hosts. The connecting user is \texttt{root} until a marker file created by the bootstrap shows that the service account exists, and \texttt{ansible} afterwards.


\subsection{Playbooks}

\paragraph{Bootstrap.} A fresh droplet only accepts the SSH key installed by DigitalOcean for \texttt{root}. The bootstrap therefore runs in two phases, driven by the Makefile target \texttt{bootstrap}. In the first phase, the playbook connects as \texttt{root} and applies only the \texttt{ansible\_user} role (tag \texttt{ansible\_user}). The Makefile then creates the marker file, regenerates the inventory so that it uses the new account, and in the second phase applies the remaining roles as \texttt{ansible} with privilege escalation: the hardening roles on all hosts, fail2ban on the bastion, and, on the application servers, the container runtime (\texttt{docker\_runtime}), the host metrics exporter (\texttt{observability}) and, on the frontend only, the TLS certificate and nginx (\texttt{nginx\_tls}). The \texttt{when} conditions rely on a fact computed in a \texttt{pre\_task}, and the play runs one host at a time by default (\texttt{serial}). The playbook \texttt{migrate-to-ansible-user.yml} performs the first phase on hosts that were provisioned earlier and were still configured through \texttt{root}.


\paragraph{Deployment.} \texttt{deploy.yml} creates a time-stamped directory under \texttt{/opt/deployments}, logs the hosts in to the GitHub Container Registry with the \texttt{registry\_login} role, then applies the \texttt{app\_backend} role to the backend group and the \texttt{app\_frontend} role to the frontend group, each with a configurable \texttt{serial} so that hosts are updated one at a time, runs the \texttt{verify} role on all hosts, and, if a Slack webhook is defined in the environment's variables, posts a notification. The Makefile exposes it as \texttt{make deploy ENV=staging|production}, with optional \texttt{TAGS} and \texttt{LIMIT} variables and a \texttt{DEPLOY\_VERSION} variable. The images \texttt{ghcr.io/oubellaismail/spring-boot-backend} and \texttt{react-frontend} are referenced with the tag \texttt{<DEPLOY\_VERSION>-<env>}, which matches the tags pushed by the continuous-integration pipeline when \texttt{DEPLOY\_VERSION} is the commit SHA.

\subsection{Secrets and Environments}

Secrets are managed with Ansible Vault. Each environment has its own \texttt{vault.yml} under \texttt{group\_vars/}, committed only in encrypted form (AES-256), and the plain \texttt{main.yml} of the same folder refers to the secrets by name, for example \texttt{jwt\_secret: "\{\{ vault\_staging\_jwt\_secret \}\}"}; the variables expected in each vault include the database credentials, the application user (\texttt{vault\_app\_user\_username}, \texttt{vault\_app\_user\_password}) and the signing secret. The vault password lives in a git-ignored file (\texttt{.vault\_pass}) that the Makefile passes to every command. The non-secret variables of \texttt{main.yml} capture the differences between the environments: domain names, the registry paths and tags of the container images (GHCR), resource limits of the containers, the choice between the staging and production certificate authorities, backup and monitoring settings.

\section{CI/CD with GitHub Actions}
\label{sec:impl-cicd}

The workflows of \texttt{.github/workflows/} implement the pipeline of Figure~\ref{fig:ci-cd-pipeline}. Two application pipelines (backend and frontend) call reusable security workflows, one workflow handles the infrastructure, and the deployment stage is only partly automated, as explained in Section~\ref{sec:impl-cd}.

\input{figures/fig5-2}

\subsection{Backend Pipeline}

\texttt{ci-back.yaml} runs on every push to any branch that touches \texttt{back/} or the workflow files, and on pull requests to \texttt{main}. It contains four jobs chained with \texttt{needs}. The \texttt{build} job compiles the project on Java~21 with \texttt{./mvnw clean install}. The \texttt{test} job runs \texttt{./mvnw test} and sends the JaCoCo report to Codecov with a repository secret. If both succeed, \texttt{build-and-push-docker} logs in to Docker Hub and to the GitHub Container Registry (GHCR), builds the image with Buildx using the GitHub Actions cache, and pushes it to GHCR under a tag made of the commit SHA and the suffix \texttt{-staging}. The tag is exposed as a job output and passed to the last job, which calls the reusable workflow \texttt{security-scans.yaml}.



\subsection{Frontend Pipeline}

\texttt{ci-front.yaml} has the same structure. The job \texttt{build-and-test} sets up Node~20 with the npm cache, installs dependencies with \texttt{npm ci}, builds the application and runs the tests non-interactively (\texttt{npm test -{}- --watchAll=false --ci}). The job \texttt{build-and-push-docker} publishes the image \texttt{react-frontend} to GHCR with the same tagging scheme, and \texttt{security-scans} calls \texttt{front-security-scan.yaml}.

\subsection{Security Workflows}

The two reusable workflows are triggered with \texttt{workflow\_call} and receive the image tag as input. Their permissions are limited to reading the repository and the packages and to writing security events. The backend workflow chains the following steps.
\begin{itemize}
  \item \textbf{Gitleaks} scans the full history (the checkout uses \texttt{fetch-depth: 0}) for committed secrets.
  \item \textbf{OWASP Dependency-Check} analyzes the Maven dependencies in HTML and SARIF formats; the SARIF run is configured with \texttt{--failOnCVSS 7}. Reports are stored as workflow artifacts, and the SARIF file is uploaded to GitHub code scanning.
  \item \textbf{Semgrep} performs static analysis with the \texttt{p/ci} rule set.
  \item \textbf{Trivy filesystem scan} first produces a SARIF report of HIGH and CRITICAL findings (exit code~0) that is uploaded to code scanning, and is then run a second time as a gate with \texttt{--exit-code 1 --severity CRITICAL --ignore-unfixed}, so that a fixable critical vulnerability fails the job.
  \item \textbf{Trivy image scan} logs in to GHCR, scans the image that has just been pushed, uploads the SARIF report and finally fails the job if any HIGH or CRITICAL vulnerability is found in the image.
\end{itemize}
The frontend workflow (\texttt{front-security-scan.yaml}) applies the same Gitleaks, Semgrep and Trivy filesystem and image steps, restricted to \texttt{front/}. Instead of Dependency-Check, it runs \texttt{npm audit}, whose JSON report is archived as an artifact; this step is report-only because the command is followed by \texttt{|| true}. It ends by writing a summary table to the job summary page.



\subsection{Infrastructure Workflow}

\texttt{terraform.yaml} can be started manually with the target environment as a choice input, runs on pushes to \texttt{main} that modify \texttt{infra/}, and is scheduled every Monday at 06:00 UTC. A scheduled run only performs the drift detection described below: the \texttt{plan} and \texttt{apply} jobs are skipped when the event is a schedule. The \texttt{plan} job installs Terraform 1.9.5 with the Terraform Cloud token, runs the scanners \textbf{tfsec} and \textbf{Checkov}, initializes the backend, selects or creates the workspace named after the environment (after validating the name against the two allowed values and passing it through an environment variable instead of interpolating it into the script, which prevents shell injection), validates the configuration and produces the plan, which is also converted to JSON for the policy check. \textbf{Conftest} then evaluates the policies of \texttt{infra/policy} against the plan, and the binary plan is uploaded as an artifact. The \texttt{apply} job depends on \texttt{plan}, runs only for a push or a manual run on the \texttt{main} branch, targets a GitHub \emph{environment} of the same name as the workflow input (so that protection rules such as required reviewers can be attached to it), downloads the saved plan and applies exactly that plan, ensuring that what was scanned is what is deployed.



The \texttt{drift-detect} job runs only on scheduled executions. It selects the staging workspace, runs \texttt{terraform plan -detailed-exitcode}, and the exit code~2, which signals a difference between the code and the real infrastructure, triggers the creation of a GitHub issue from the template \texttt{.github/drift-template.md} with the labels \texttt{drift}, \texttt{infra}, \texttt{staging} and a priority. The same sequence is then repeated for production, if the workspace exists, with a critical priority label.


A second workflow, \texttt{opa-policy-check.yaml}, is triggered by pull requests that change files under \texttt{infra/}. It runs in the \texttt{infra} directory, produces a plan, renders it as JSON and evaluates \texttt{data.terraform.security.deny[\_]} with \texttt{opa eval --fail-defined}, which fails the check as soon as any deny rule yields a message (querying the set itself would not work, since an empty set is still a defined value). Violations are thus reported on the pull request before the merge, while the Conftest step of \texttt{terraform.yaml} acts as a second barrier on the main branch.


\subsection{Continuous Deployment}
\label{sec:impl-cd}

Deployment automation is the least complete part of the pipeline. \texttt{cd-back.yaml} is triggered by the completion of the workflow \texttt{Terraform Infrastructure}; it runs only if that run succeeded and was not a scheduled run, then opens an SSH session on a server whose address, user and key are repository secrets, updates a checkout, pulls the images and restarts the Compose services. It is a plain \texttt{docker compose up -d} on one host, with no rolling update, no automatic rollback and no call to the Ansible playbooks. Because it follows the infrastructure workflow rather than the application pipeline, it is a coarse mechanism rather than a release process. \texttt{cd-front.yaml}, triggered after the frontend CI, only prints a placeholder message. The deployment path that exercises the complete configuration is the Ansible command \texttt{make deploy} of Section~\ref{sec:impl-ansible}, launched by an operator. Note that the continuous-integration pipeline only builds images tagged with the commit SHA and the suffix \texttt{-staging}; a production deployment therefore requires an explicit image tag.
